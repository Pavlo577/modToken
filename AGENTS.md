# Token Tracker (OTLP): notes for agents working here

A tracker of AI-agent token usage from many devices, built only on OpenTelemetry: a Cloudflare Worker + D1 + a static dashboard (`worker/`), and `docs/OTLP.md` for the data. No collector program or hook (the older design lives on the `claude` / `dev` branches). Two exceptions, both because OTLP cannot carry the data: the **`token-tracker` mod** (`worker/mods/token-tracker`) sends what only the session knows, as numbers: the subscription's rate-limit windows (`POST /v1/limits`), and sessions and main-loop turns (`POST /v1/activity`: start and end, wall-clock time, the pause before a prompt, context fill, permission prompts), plus the session's repository (owner/name or a hash) only when the device's `project_mode` allows it; never tokens, which come from OTLP alone; and the history import, which parses Claude Code's local logs **on the device** (`src/history.ts`: in the browser from the dashboard, or in the mod's `/tracker-import`, whose `hooks/history.ts` must stay a byte-for-byte copy, `test/history.test.mjs` checks it) and sends numbers only (`POST /api/admin/import`, `POST /v1/import`, both through `src/import.ts`); never move that parsing to the server. In a cloud session the mod is installed by `worker/scripts/cloud-setup.sh` and loaded through `CLAUDE_CODE_PLUGIN_DIRS`. User-facing text is Ukrainian; code, comments and docs are English.

## Rules
- **Only numbers are kept**: token counts, timestamps, model names, ids. Never store, print or log prompts, answers, tool output, `cwd`, file contents, emails or account ids. The one thing that cannot be avoided, decided by the user: Claude Code adds `user.email` and account ids to its events; the Worker drops them on arrival (`worker/src/otlp.ts`: an allow-list, not a block-list) and the tests check it.
- The events database (`EVENTS`) keeps every event's attributes through `safeAttrs` only: numbers, flags and identifier-like words, never identity or text. Do not widen that filter; add a test with a planted secret if you touch it.
- **Every field an agent sends is listed in `worker/src/otlp-fields.ts`** (the registry: name, events, type, meaning, what the Worker does with it). A new field is added there, then `bun run fields` regenerates `docs/OTLP-fields.md` (never edit that file by hand); `test/fields.test.mjs` fails when the registry and the code disagree, and the Insights tab lists fields that arrive but are missing from the registry.
- A new agent is a new adapter in `worker/src/otlp.ts` (`ADAPTERS`, keyed by `service.name`) that returns `ModelCall`s, a test with a synthetic payload that plants a secret word and checks it never reaches the result, and a row in `docs/OTLP.md`. Event and attribute names must come from the agent's own documentation or a real payload, never a guess.
- The mod sends numbers only: `worker/src/limits.ts` and `worker/src/activity.ts` read named fields and drop the rest (`test/limits.test.mjs`, `test/activity.test.mjs` plant secrets). The project is the one name it may send, and only as far as `devices.project_mode` (off | name | hash) allows: the server checks it again, and turning it down forgets what was stored. Never prompts, answers, tool input or output, paths. The names of fields the mod sends but the Worker does not read are remembered (`worker/src/dropped.ts`, table `otlp_seen`, service `token-tracker`; names only, never values) and show in the Insights "new fields" card. A field the mod starts to send is read in `limits.ts` / `activity.ts` / `import.ts` and added to `MOD_FIELDS` in `dropped.ts`. Do not make it send tokens: OTLP is their one source, two would count twice.
- **Rows read are limited per day** (D1 free plan: 5 million). Every query on the hot path (the OTLP receiver runs on every export, every few seconds per session) must use an index: filter by `user_email`/`device_id` first, never `WHERE ts < ?` or `LIKE` alone on a big table. The Insights page runs ~20 queries, so it is cached for two minutes (`?fresh=1` skips the cache).
- Never commit secrets, device tokens or real session data. Test fixtures are synthetic.
- Push to `main` (it goes live) only when the user says so. Applying `migrations/*.sql` to the production database needs the user's explicit confirmation.

## Commands (from `worker/`)
- `npm test` and `bun test` must both pass; `bun run typecheck`.
- End to end: fresh local DB (`rm -rf .wrangler/state && bun run db:local`), `npx wrangler dev --port 8787` (`DEV_EMAIL` from `.dev.vars`), then `bash test/otlp.sh`; `bash test/gate.sh` against a server started without `DEV_EMAIL`.
- The dashboard is built by `bun run build` (web/ → public/admin/app.js, not committed).
